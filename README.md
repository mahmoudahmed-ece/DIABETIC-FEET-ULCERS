Firmware for a **smart shoe that monitors the feet of diabetic patients** to help prevent
**diabetic foot ulcers**. The system measures plantar pressure, foot temperature and humidity,
combines them into a **risk score**, raises an alert when the risk is high, and streams every
reading over UART as CSV for logging and analysis.

> **Status:** Phase 1 — firmware ported from an Arduino prototype to the STM32F103 ("Blue Pill") and validated in Proteus VSM.

---

## Why These Measurements

Diabetic foot ulcers usually start from problems the patient cannot feel because of nerve damage:

| Risk factor | What the firmware measures | Sensor |
|---|---|---|
| Sustained high pressure on one area of the foot | Pressure at the heel, midfoot and forefoot | 3 × FSR (force-sensitive resistor) |
| Inflammation (a hot spot before an ulcer forms) | Temperature difference between two zones of the foot | 2 × LM35 |
| Excess moisture (skin breakdown, infection risk) | Relative humidity inside the shoe | DHT11 |

## Pin Configuration

| STM32 Pin | Function | Connected To |
|:---:|---|---|
| **PA0** | ADC1_IN0 | FSR — Heel |
| **PA1** | ADC1_IN1 | FSR — Midfoot |
| **PA2** | ADC1_IN2 | FSR — Forefoot |
| **PA3** | ADC1_IN3 | LM35 — Zone 1 |
| **PA4** | ADC1_IN4 | LM35 — Zone 2 |
| **PB0** | GPIO (bit-banged one-wire) | DHT11 data |
| **PA8** | GPIO output | Buzzer (alert) |
| **PA9 / PA10** | USART1 TX / RX | Serial terminal (9600-8-N-1) |

## How It Works

Every **500 ms** the firmware takes one snapshot of all sensors:

1. **Pressure:** reads the three FSRs through ADC1 (12-bit, 0–4095).
2. **Temperature:** reads both LM35 sensors through ADC1 and converts them to °C.
3. **Humidity:** reads the DHT11 with a bit-banged one-wire protocol, timed with a microsecond delay built on the Cortex-M3 **DWT cycle counter**.
4. **Risk score:** fuses the readings into a score from 0 to 100.
5. **Output:** sends the snapshot as a CSV line over USART1 and drives the buzzer.

### Risk score model

| Condition | Points |
|---|:---:|
| Highest pressure reading > 3300 (ADC counts) | +40 |
| Temperature difference between the two zones > 2.2 °C | +40 |
| Humidity > 70 % (when the DHT11 reading is valid) | +20 |

The score is capped at 100. When it reaches **60 or more**, the buzzer on PA8 turns on.
All thresholds are `#define` constants at the top of the firmware, so they can be tuned easily.

### CSV output (USART1, 9600 baud)

```
timestamp_ms,heel,midfoot,forefoot,temp1_C,temp2_C,humidity_pct,risk_score
1500,812,640,2950,31.25,31.70,48.0,0
2000,3410,655,2980,31.30,33.80,72.0,100
```

A humidity value of `-1.0` means the DHT11 reading failed its checksum or timed out.

## Building

The firmware uses the STM32 HAL. The peripheral initialization (`SystemClock_Config`,
`MX_GPIO_Init`, `MX_ADC1_Init`, `MX_USART1_UART_Init`) is normally generated by **STM32CubeMX**.

**Option 1 — STM32CubeIDE**

1. Create a CubeMX project for the STM32F103C8T6.
2. Configure ADC1 channels 0–4 (PA0–PA4), USART1 at 9600-8-N-1 (PA9/PA10), PA8 as GPIO output and PB0 as GPIO.
3. Copy the logic from `smart_shoe_stm32_phase1.c` into the `USER CODE` sections of the generated `main.c`.

**Option 2 — CMake**

1. Install the GNU Arm Embedded toolchain (`arm-none-eabi-gcc`) and set its path in `arm-none-eabi.cmake`.
2. Add ST's `Drivers/` folder (STM32F1 HAL + CMSIS) and the CubeMX `Inc/` and `Src/` files to the project root.
3. Build:
   ```bash
   cmake -B build -G "Ninja"
   cmake --build build
   ```
   The build produces `.elf`, `.hex` and `.bin` files.
